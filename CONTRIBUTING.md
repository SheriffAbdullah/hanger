# Contributing to Hanger

Thanks for helping. Hanger is early beta, so the most useful contributions right now are real-world reports: does the report give IT what it needs, did it get a diagnosis wrong, is a signal missing. The issue templates are set up for exactly that.

## Ground rules

- **Evidence, not verdicts.** Hanger never tells anyone what to buy or who deserves which machine. Action text suggests checks, not purchases.
- **IT is the reader.** Reports are written for the IT / tech-ops team that has to act on them; the developer is the collector. Wording that treats either side as an adversary will be asked to change.
- **Privacy by declared scope.** Software outside the declared scope is only ever an anonymous aggregate. Nothing may phone home. Zero runtime dependencies: Node built-ins and PowerShell only.
- **Be honest in docs.** Do not claim a feature that is not implemented, or call something validated that is only checked against fixtures.

## Workflow

1. Open an issue first for anything larger than a small fix, so we agree on the shape.
2. Fork, then create a branch from `main` (`fix/short-name` or `feat/short-name`).
3. Make the change in small, focused commits.
4. Open a pull request against `main` and fill in the template.

## Spec-driven changes (OpenSpec)

Behavior changes start as an OpenSpec change, not as code:

```powershell
openspec new change my-change          # creates openspec/changes/my-change/
# write proposal.md, design.md, specs/<capability>/spec.md deltas, tasks.md
openspec validate --all --strict
```

Requirements use `SHALL`/`MUST`, every requirement has at least one `#### Scenario:` with GIVEN/WHEN/THEN, and tasks say how each one is verified. Completed changes are archived under `openspec/changes/archive/`, which is historical record and is not edited.

## Run the checks

```powershell
node --test tools/hanger/test/        # the whole zero-dependency suite
node tools/hanger/test/canary-leak.js # privacy canary: must print "canary hits: 0"
openspec validate --all --strict      # specs
```

The **privacy canary must stay green.** It runs the tool against a planted secret and fails if any file, log or console line names software outside the declared scope. A change that touches collection, rendering or persistence must not weaken it. Run the canary with no other window stealing focus; one check watches the foreground window.

## Schema and fixtures

The report schema (`hanger-json/2`) is frozen. Additive fields go in a dated entry in `tools/hanger/SCHEMA-CHANGELOG.md`; a removal or rename bumps the schema. Fixtures are generated by `tools/hanger/test/fixtures/build-*.js`; regenerate rather than hand-editing them, and use synthetic data only. Never commit a real hostname, username, serial number or process list.

## Style

Plain Node, no build step, no new dependencies. Match the surrounding code. Console messages are prefixed `[hanger]`.

## Conduct

Participation is covered by the [Code of Conduct](CODE_OF_CONDUCT.md). Security issues go through [SECURITY.md](SECURITY.md), not public issues.
